# 研发团队协作与交付规范

星舟科技有限公司  研发限定示例 仅供获授权人员

文档编号：XT-RD-2026-03；版本：1.0；示例生效日期：2026-11-19。

虚构研发团队资料，仅用于知识库和权限测试；项目、环境、时间窗口及流程均为模拟设定，不含真实密钥。

## 一 团队范围与需求管理

本规范供获授权的研发、测试及发布协作人员查询需求澄清、技术设计、代码评审、测试验收和发布回滚流程。相关动作通过企业既有研发平台和人工审批执行；知识助手负责查询依据，不创建真实任务、不合并代码、不部署生产环境。

### 第1条 访问范围和示例项目

本资料应存放于“研发团队资料”或对应的受限知识库，仅向经过批准的人员授权。部门名称、职级或其他同事的账号不能替代授权。不得将本资料的完整正文或专属内容复制到企业公共制度库，再以“方便检索”为由向全员开放。

本文使用虚构的“星穗检索优化项目”说明流程，其研发专属识别标记为RD-STAR-7416。该标记只用于检验受限资料检索，不是密码或访问凭据。示例项目当前处于需求评审阶段，本文没有给出正式上线日期，不应由助手推断某个确定交付日。

### 第2条 需求登记与评审

需求负责人提交业务背景、目标用户、问题描述、范围、验收条件、相关依赖和提出人。研发负责人组织产品、开发和测试共同澄清，在正式评审前将材料提供给参加人员，通常至少预留1个工作日供阅读。关键依赖未明确时，应记录待确认项和负责人。

需求状态依次记录为待澄清、已评审、实施中、待验收、已完成或已取消。只有明确通过评审的范围才能作为当前开发基线；讨论中的方案、聊天建议和临时口头要求不自动成为已批准需求。范围变化应更新原任务并说明对工作量、测试和交付的影响。

### 第3条 责任与优先级

| 角色 | 主要职责 |
| --- | --- |
| 需求负责人 | 说明业务问题，维护范围和验收条件，对需求变更和业务验收给出结论。 |
| 研发负责人 | 组织设计与评审，明确人员和依赖，核对技术风险与实施安排。 |
| 开发与测试 | 实现与验证变更，提供复现步骤、测试证据和未解决问题。 |
| 发布及值守人员 | 按授权执行发布，核对观测结果与回滚准备，处理线上异常。 |

需求优先级P0表示阻断核心业务或涉及重大数据、权限风险，P1表示重要交付，P2表示一般优化。需求优先级与第五章的事故级别是两套记录，不能仅凭一个P0标签跳过代码评审或安全检查。

## 二 技术设计与代码协作

### 第4条 设计与接口约定

涉及跨服务、权限、数据库或费用规则的变更，应先说明处理流程、数据来源、接口请求与响应、失败路径、兼容性及回滚方式。接口字段应注明类型、是否必填、单位、取值范围和错误原因。金额、时间和身份字段不能仅依靠模型或页面提示词保证正确。

设计中明确哪些值由用户确认、哪些来自服务端权威数据、哪些由程序计算。需要管理员核对的来源和规则，应保留版本与修订记录。涉及数据结构变化时，应准备迁移步骤和失败恢复方式，不能让运行时悄悄删除旧数据以“修复”兼容问题。

### 第5条 分支与变更说明

本示例团队将main作为已核对版本的主分支，功能分支使用feature/任务编号，缺陷修复使用fix/任务编号，紧急修复使用hotfix/事件编号。名称是团队约定，不表示当前知识问答项目已经配置相同仓库或流水线。提交应聚焦一个可说明的变更目的。

变更申请说明解决的问题、触发条件、修改后的行为、验证方法和已知限制；涉及用户行为变化时给出可对照的前后示例。不要在变更正文、提交记录或截图中写入密码、Key、生产数据、客户信息或无关私人内容。

### 第6条 代码评审

普通变更至少由1名非作者完成评审后再合并。涉及鉴权、金额计算、数据库迁移或敏感数据时，还需相关领域负责人确认；作者不能以自己已经测试代替独立评审。材料完整后，评审人通常在1个工作日内反馈是否可以开始评审，不承诺所有变更都能在当天通过。

评审结论分为通过、需修改、待补材料。超时没有回复不等于默认通过；冲突未解决、测试失败或风险说明缺失时应继续补齐。评审意见应针对具体行为和证据，不能只以代码风格或模型回答流畅来判断业务正确。

### 第7条 合并前检查

合并前核对接口兼容、错误处理、权限边界、依赖配置和必要测试。需要人工执行的迁移或环境操作应列出负责人及验证方式。文档、示例配置和运行说明应与变更一起更新，不将仅在开发者机器上手动设置的内容当作完整交付。

发现配置或凭据缺失时，应报告缺少的项目和配置位置，不把真实密钥写入仓库作为“默认值”。公开示例使用占位内容，受限配置通过获批准的渠道交接。

## 三 环境数据与测试验收

### 第8条 环境和访问职责

| 环境 | 用途 | 访问与数据边界 |
| --- | --- | --- |
| 开发环境 | 编码、自测和局部联调 | 使用虚构或批准的测试数据，不默认读取生产业务库。 |
| 测试环境 | 接口联调、回归与业务验收 | 测试数据可重建；与生产账号、存储和费用账本区分。 |
| 生产环境 | 向实际用户提供服务 | 仅授权发布与值守人员按流程操作，不向全体研发默认开放。 |

各环境应使用明确区分的数据库、存储目录、回调地址和凭据。复制故障案例到测试环境时，只保留复现所必需的最少信息并按要求去除敏感数据；不能把完整生产库下载到个人设备来方便调试。临时访问应写明用途和期限，完成后收回。

### 第9条 测试计划与依据

测试负责人根据需求范围列出正常流程、边界、失败、权限和并发场景，确定前置状态、输入、独立预期和恢复步骤。预期金额、数量或状态不能直接调用被测函数生成，再用相同实现证明自己正确。尚未执行、受阻和失败应分别记录。

涉及知识助手时，既要验证来源真实、当前有效和可访问，也要人工比较结论是否受到引用支持。资料存在不等于答案全部正确；不能只数引用按钮或把模型自动评分当成完整业务验收。真实模型效果与替身验证的确定性边界分开报告。

### 第10条 核心回归与缺陷

修改登录、角色或知识库授权，要验证未登录、跨用户、撤权后的读取与历史上下文。修改费用规则和预算，要验证职级来源、条件确认、单位、金额以及缺失或冲突时不出伪完整合计。修改文档更新流程，要验证失败不覆盖有效旧版、成功后来源切换及关联规则状态。

缺陷记录包含版本、账号与权限、输入、操作步骤、实际和预期结果、时间及必要证据。权限泄露、错误金额、编造制度或错误引用归属必须修复并复测，不能由其他题目的得分抵消。复测保留原失败记录，不反复重跑只挑成功的一次。

### 第11条 验收记录

测试结论应列出执行数量、未执行项、失败与阻塞原因、环境差异和残余风险。变更后完成受影响用例及必要回归，业务负责人再给出范围内验收结论。测试平台通过、开发自测通过和业务验收是不同记录，不得互相代签。

## 四 发布准备与回滚

### 第12条 常规发布窗口

本示例团队常规发布窗口为每周二、周四15时至17时，使用北京时间。发布申请原则上在前一个工作日16时前提交，说明版本、范围、影响、负责人、验证方法和回滚方案。遇到非工作日或特殊活动，由发布负责人另行确认；未确认时不自动顺延并视为已经获批。

发布窗口只是可安排的时间范围，不是项目的承诺上线日。未完成评审、验收或授权，即使到达窗口也不能发布。紧急修复需值守负责人及相关业务负责人批准，记录原因和补审安排；紧急情形不取消权限和数据核对。

### 第13条 发布检查清单

| 检查项 | 应保留的依据 |
| --- | --- |
| 变更版本 | 明确的版本标识、构建产物和对应变更记录，能够回溯具体修改。 |
| 评审与测试 | 必要评审结论、回归结果、业务验收状态及尚未解决的风险。 |
| 配置与迁移 | 配置差异、授权人员、迁移步骤、备份或兼容性说明。 |
| 验证与回滚 | 关键场景、观测指标、值守分工、回滚版本及执行方式。 |

发布前确认需要的配置和外部服务可用，但不在申请单写真实密码或Key。涉及数据库的操作先核对目标环境，涉及不可逆变化时准备经过评估的恢复路径；不能假设所有迁移都可通过简单回滚程序版本恢复。

### 第14条 发布后验证

执行人记录开始时间、各步骤结果和完成状态。发布后至少持续观察30分钟，验证健康状态、登录、关键业务请求、错误率及必要的数据一致性。具体阈值由发布申请明确，不能用“页面能打开”代替全部验证；观察期间安排可联系的值守人。

### 第15条 回滚触发与决策

出现核心业务中断、权限泄露、错误金额或明显数据不一致时，应先控制影响并通知值守负责人。满足已约定回滚条件时按方案执行；条件不明确或涉及数据修复时，由授权负责人协调判断，不由知识助手或单条聊天指令直接执行生产操作。

回滚后核对功能恢复、数据状态、在途请求和残余风险，记录回滚版本、原因和时间。回滚不等于故障原因已经解决，后续修复应重新经过评审、测试和批准。

## 五 事故归档与知识复用

### 第16条 事故分级与响应

| 级别 | 示例影响 | 本示例响应目标 |
| --- | --- | --- |
| S0 | 核心业务大范围中断、权限泄露或严重数据风险 | 10分钟内响应并通知负责人，30分钟内评估控制或回滚方案。 |
| S1 | 重要功能故障，影响明确用户群但存在替代方式 | 30分钟内响应，2小时内提供处理计划或阶段结论。 |
| S2 | 局部非关键缺陷或一般性能体验问题 | 1个工作日内受理并确认后续安排。 |

响应目标用于组织接收、分派和决策，不保证在同一时限内完成修复。事件记录应持续补充影响范围、当前措施和下一次沟通时间。涉及安全或隐私风险时，仅在授权范围传递必要证据，不能把泄露原文复制到公共事故群或公共知识库。

### 第17条 复盘与资料归档

S0或S1事件恢复后，通常在2个工作日内提交初步复盘，说明时间线、触发条件、影响、处理、根因及改进项。尚未查明的原因应明确写待确认，不将猜测或模型推断写成已证实事实。改进项列明负责人、计划时间和验证方法，完成后补充证据。

研发项目交付应归档需求与验收、设计与接口、关键评审、测试证据、发布及回滚记录。研发项目差旅还需归档项目编号和差旅工作记录；该附加要求不修改企业公共住宿标准或80元日补贴，也不能作为新增费用单价的依据。

### 第18条 研发资料维护

负责人发布新版本前核对适用项目、内容分级、版本与有效性，管理员只向获授权人员开放。整理可公开经验时先去除项目专属标记、内部窗口、受限数据和真实配置，再由负责人确认公开范围；不能直接把受限文档改名为公共资料。

当前知识问答系统只能基于当前有效且授权的资料给出说明，不具备本文所述的真实研发平台、代码仓库、CI、发布或事故执行能力。文档入库也不会自动创建任务、设置仓库保护、审批发布或调整系统角色。

### 第19条 常见问题

问：评审超过一天没有回复，可以自动合并吗？答：不能，超时不等于通过。问：到了周二发布窗口，是否就能上线？答：还需必要评审、验收和明确批准。问：响应10分钟表示10分钟修复吗？答：不表示，响应与恢复是不同节点。

问：测试都通过后能替业务负责人签字吗？答：不能。问：项目正式上线是哪一天？答：本文没有提供确定上线日期。问：未获授权的同事如何查阅本资料？答：先通过负责人申请权限，不能借用他人账号或复制到公共库。
