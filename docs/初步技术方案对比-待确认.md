## T01：开发路线

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | Python + Django + 模板页面与少量 JavaScript | 可复用账号、会话及内部管理后台，减少后台基础页面工作 | 员工聊天页面仍需制作；按知识库授权需实现业务校验；前后端独立工程的展示空间较少 |
| B | Python FastAPI + Vue 前后端分离 | 接口与页面职责清楚，FastAPI 可生成交互式 API 文档，适合展示完整前后端工程 | 需要额外选配或制作后台与账号管理，并学习前端构建与接口联调 |
| C | Python + Streamlit | 便于快速制作数据和聊天交互原型 | 知识库授权、后台管理和持久会话仍需设计；已有身份认证能力不代替业务授权 |

原推荐 A；第五轮已确认 B，后续按 FastAPI + Vue 设计。

参考：[Django 管理后台](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/)、[Django 账号与权限](https://docs.djangoproject.com/en/5.2/topics/auth/)、[FastAPI 功能](https://fastapi.tiangolo.com/features/)、[Streamlit 身份认证](https://docs.streamlit.io/develop/concepts/connections/authentication)。文档版本不代表已选项目依赖版本。

## T02：业务与向量数据存储

业务数据库保存账号、权限、文档元数据、计算规则和会话。向量索引用于按语义检索文档片段。

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | SQLite + 本地持久化 Chroma | 本机启动依赖较少，可保存业务数据和向量索引 | 两套逻辑存储，需要处理文档状态、替换、删除和重建的一致性 |
| B | PostgreSQL + pgvector | 在同一数据库中组织业务与向量数据，便于 SQL 查询及一致性设计 | 需要安装运行数据库与扩展，环境配置工作较多 |

原推荐 A；第五轮已确认 B，后续按 PostgreSQL + pgvector 设计，关键词分词、索引与排名融合继续细化。

参考：[Chroma 本地持久化](https://docs.trychroma.com/docs/run-chroma/clients)、[Chroma 元数据过滤](https://docs.trychroma.com/docs/querying-collections/metadata-filtering)、[pgvector 官方仓库](https://github.com/pgvector/pgvector)。

## T03：对话模型与文本向量化

文本向量化把文档片段与问题转换成可用于语义匹配的数值表示。它与生成最终答案的对话模型承担不同工作。

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | 同平台的对话与向量 API，候选阿里云百炼 | 账号配置较集中，无需先安装本地向量模型 | 两类调用均需计费与联网；具体对话型号、向量型号、工具调用能力及额度待验证 |
| B | 外部对话 API + 本地向量模型 | 向量化可在本机进行，减少外部向量调用 | 增加模型下载、运行依赖和本机性能验证工作 |
| C | 优先评估用户已有的 API 资源 | 可复用已有账号和额度 | 需要先确认供应商、对话/向量能力、价格和可访问性 |

第五轮已确认 A，采用百炼对话与文本向量 API。具体型号、地区、适配器与费用参数继续比选。

预算测算需分别统计文档向量化、问题向量化、每次模型请求的输入输出，以及补查和重试。约 100 元是预算目标，尚未测得真实请求成本或可支持次数。

参考：[百炼模型列表](https://help.aliyun.com/zh/model-studio/models)、[文本向量 API](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)、[调用价格](https://help.aliyun.com/zh/model-studio/model-pricing)。账号地区、型号和调用方式确认后重新核算费用，不默认依赖免费额度。

## T04：检索策略

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | 向量检索基线 | 能处理语义相近的不同问法，便于先建立可评估链路 | 精确制度名称、编号和专用词可能需要补充手段 |
| B | 关键词 + 向量混合检索 | 结合精确词匹配与语义匹配 | 需要验证中文分词、排名融合和索引更新 |
| C | 混合检索 + 重排序 | 对候选片段进一步评分，可能改善排序 | 增加模型调用或本地计算，效果需要实测 |

原推荐 A；第五轮已确认 B，混合检索属于首版交付。纯向量可用于对照评测；C 仍为增强候选。自动补查与检索策略分别实现和验证。

参考：[混合检索原理](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)。本项目是否采用 Azure 未进入选项，该来源用于核对检索原理。

## T05：受控 Agent 编排

三种方案都应覆盖已确认的有限补查能力；工具授权、参数校验、调用与耗时上限均需设计。

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | Python 编写小型受控工具调用循环 | 工具少时便于理解和逐步调试，依赖较少 | 需明确编写停止条件、错误处理和状态管理 |
| B | LangChain Agent | 提供模型、工具调用循环与中间件等封装 | 需要学习抽象、适配模型并跟进依赖版本 |
| C | LangGraph 状态图 | 便于明确表达条件分支、状态和可恢复步骤 | 抽象层较低，初学者学习与流程配置工作更多 |

原推荐 A；第五轮已确认 B，采用 LangChain Agent。实际权限与计算公式仍由程序控制；补查限额、适配器和框架版本继续确认。

参考：[LangChain Agent](https://docs.langchain.com/oss/python/langchain/agents)、[LangGraph 概览](https://docs.langchain.com/oss/python/langgraph/overview)。

## T06：引用定位与预览

| 选项 | 方案 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A | 文档名 + 引用片段 | 实现较轻，可核对答案文字依据 | 查找原文位置需要更多人工操作 |
| B | 引用片段 + 可靠位置锚点 + 授权下载原文件 | PDF 显示可验证页码，Word/Markdown 显示章节或段落位置，便于追溯 | 解析时需保留锚点，缺少标题时需有可解释的回退定位 |
| C | 页面内完整原文预览和精确高亮 | 阅读体验更完整 | 多格式预览、版面坐标与高亮处理工作较多 |

第五轮已确认 B。Word 不默认使用固定页码；无法可靠获得定位时提示可用片段及位置状态。下载与引用访问遵守已确认的知识库授权。
