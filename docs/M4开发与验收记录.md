## 员工使用流程

1. 登录`employee_li`，输入“我去北京出差3天，住宿2晚。请帮我估算住宿和补贴预算”。
2. Agent调用`propose_trip_context`，生成“北京、3天、2晚”的待确认卡。该提议保存到消息，**不写入已确认会话条件，也不计算金额**。
3. 员工核对后点击“确认条件并计算”。前端明确保存条件revision，再提交绑定条件revision与员工资料revision的预算确认请求。
4. Agent调用无价格/身份参数的`calculate_travel_budget()`，程序从当前权威资料取得S1、匹配有效规则，并按十进制计算。
5. 展示住宿600.00元、补贴240.00元、合计840.00元及每项来源。点击引用可核对原文、版本、位置并授权下载。

“修改条件”可把提议填入条件卡；缺字段时先补齐再确认。条件卡也提供“确认并计算预算”，使用同一计算服务直接计算，不调用对话或向量API。条件卡手动保存只保存条件，不自动生成金额；聊天里识别的新条件仍须再次确认。

仅确认当前保存条件的revision不足以防止员工资料在此期间变化，因此预算确认同时绑定profile revision。任一变化返回409，要求刷新重确认；员工不能通过自然语言、工具参数或API字段改写职级、规则单价或授权。

## 管理员规则流程

管理入口`/admin/fee-rules`：查看规则、适用城市/职级、单价、来源、版本和可用状态。

- 新建/编辑：选择当前有效文档和片段，保留原文连续摘录；保存为草稿。修改已启用规则也会退回草稿并清除原核对记录。
- 核对启用：显示片段全文和摘录，管理员核对适用范围、单位和单价，勾选确认后启用。服务端再次校验来源、revision和重叠范围。
- 暂停：立即停止该规则参与新计算。规则保留，以维护历史关系，不提供物理删除规则接口。
- 冲突：当前同企业的有效日补贴规则不得重复，住宿规则的相同职级/城市范围不得重叠。启用操作串行校验；计算端仍防御性检查，不能任意选择第一条。

原文摘录必须真实存在且当前有效；程序不声称自动证明任意自然语言条款与手工参数在语义上完全一致。管理员核对是该业务的权威录入步骤。

## 计算边界与工程默认值

- 输入仍为1—30整数天、0≤整数晚数<天数；严格拒绝布尔值、负数、超限和越权字段。不从出差天数推断晚数。
- 城市按规则中明确名称精确匹配，去除首尾空白，不自动把“北京市”映射到“北京”，也不推断未列城市类别。自然语言提议可由员工修正。
- CNY、两位小数、Python Decimal及ROUND_HALF_UP到分为本阶段工程默认值。规则单价拒绝超过两位小数、负数、NaN/Infinity和超过999999.99元；不通过二进制浮点参与金额运算。
- 完整结果必须有全部条件和唯一可用的住宿/补贴规则。缺条件为`needs_information`，规则缺失/冲突为`blocked`，`total_amount`必须为空；允许显示有有效依据的单项金额。
- 零晚住宿可得0.00元，但仍要求目的地及相应有效标准，不借零数量绕过未知城市检查。
- 真实模型负责提取和解释；提取可能出错，须经员工核对。预算的结构化单价、数量、金额与正文由服务端计算接管，模型返回的自由文本不能覆盖计算结果。
- `calculate_travel_budget`在未收到本轮显式预算确认时，只返回待确认卡；即使旧条件已经保存，也不会据此静默计算。确认前不产生计算快照。
- 每轮5次检索/10次模型请求/90秒继续有效；提议与计算为本地工具，不计知识检索次数或对话请求次数，但受总时间与一般工具防循环保护。模型usage预留现在包括完整工具Schema。

## 来源变化与历史

每次计算核对当前用户权限、选定KB、员工资料、文档当前版本、有效期、向量空间和规则状态。

文档成功发布替换版本或删除时，在同一事务中暂停引用旧版本的已启用规则并递增revision；失败替换不发布，原有效规则不因此被停用。来源到期或知识库不可访问时，即使数据库状态尚显示active，计算也不会使用它。

历史预算通过消息的统一来源检查和规则revision检查再返回：撤权、源删除/替换/到期、规则编辑/暂停或revision变化时，相关预算正文、明细和引用整体不可用，不能通过`GET /calculations/{id}`绕过；也不进入新模型上下文。当前采用保守的整条隐藏策略，保留数据库中的原快照。重新启用规则不会把旧revision的预算变成当前有效结果，应重新计算。

上述是M4计算安全所必需的联动；不代表M5完整管理闭环已经验收。规则操作独立审计履历、版本变更的完整引导与更多管理端一致性流程仍留在M5。物理保留策略仍待细化。

## API 与持久化

统一`/api/v1`前缀和Bearer鉴权，具体Schema以本机OpenAPI为准。

| 方法 | 路径 | 契约 |
| --- | --- | --- |
| GET / POST | /admin/fee-rules | 管理员列表/创建草稿；name、kind、grade、cities、unit_rate、source_chunk_id、source_quote |
| PUT | /admin/fee-rules/{id} | 完整编辑+expected_revision；保存后退回草稿 |
| POST | /admin/fee-rules/{id}/activate | expected_revision、source_checked=true；当前原文与范围冲突复核 |
| POST | /admin/fee-rules/{id}/suspend | expected_revision；暂停规则 |
| POST | /conversations/{id}/calculations | 本人直接确认计算，返回201；client_request_id、context_revision、profile_revision，可选trip_context作为明确确认；不调用模型 |
| GET | /calculations/{id} | 只限本人会话，重新检查来源与规则；不可用返回404，不返回旧快照 |

M3消息提交额外支持成对的`budget_confirmed_revision/budget_profile_revision`：前者必须等于当前context_revision，且不能同时提交trip_context。已确认条件先保存，再确认预算；不允许混用旧版本。普通聊天不设置该标记。

消息响应新增可选`trip_proposal`和`calculation`。提议包含待确认条件及其基础revision；费用结果包含本人资料、已确认条件、项目数量/单价/金额、规则revision、来源信息、状态和完整合计。未授权的消息不返回这些字段。

迁移`0004_m4`新增fee_rules、calculations、calculation_items三表，累计20张业务表。保留规则核对者/时间、状态/revision、资料和条件快照、计算项目及来源快照；金额NUMERIC。直接计算的(actor_id,client_request_id)唯一，哈希不同则409；重发同一请求复用原结果，同会话活动问答期间不允许并发直接计算。

主要代码：`fee_protocol.py`、`services/fees.py`、`api/fees.py`、Agent两项工具和`FeeRulesView.vue`；ChatView新增待确认卡、预算明细与直接计算入口。
